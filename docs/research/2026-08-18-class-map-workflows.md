# CLASS MAP

## Spec / Agent definition (`omnigent/spec/`)
- **`AgentSpec`** — `omnigent/spec/types.py:1382-1546`. The fully parsed agent image. Fields: `llm: LLMConfig`, `tools: ToolsConfig`, `executor: ExecutorSpec`, `guardrails: GuardrailsSpec|None`, `mcp_servers: list[MCPServerConfig]`, `sub_agents: list[AgentSpec]` (recursive), `os_env`, `terminals`, `skills: list[SkillSpec]`. `executor.type` is the discriminator ("omnigent" default, "claude_sdk", "agents_sdk"); for "omnigent" the concrete harness (claude-sdk/codex/codex-native/etc.) lives in `executor.config["harness"]`, exposed via `ExecutorSpec.harness_kind` property (types.py:599-616).
- **`ExecutorSpec`** — types.py:487-616. Carries `model`, `auth: ApiKeyAuth|DatabricksAuth|ProviderAuth`, `timeout`, `max_iterations`.
- **`LLMConfig`** — types.py:644-708. model, connection, `retry: RetryPolicy`, `fallback_models`.
- **`RetryPolicy`** — types.py:42-254. Layered retry (L0 SDK-internal via per-provider adapter properties `.openai`/`.anthropic`/`.claude_cli`/`.codex_cli`/`.pi`, L2 workflow-level via `compute_backoff_delay`).
- **`GuardrailsSpec`** — types.py:1358-1378: `labels: dict[str,LabelDef]`, `policies: list[PolicySpec]`, `ask_timeout` (default `DEFAULT_ASK_TIMEOUT=86400`, types.py:39).
- **`PolicySpec`** (base) / **`FunctionPolicySpec`** (subclass) — types.py:1291-1354. `on: list[PhaseSelector]`, `condition` (label-gate), `function: FunctionRef`.
- **`MCPServerConfig`** — types.py:861-975. transport `"http"|"stdio"`, redacting `__repr__`.
- Parser/validator: `omnigent/spec/parser.py`, `omnigent/spec/validator.py` (not read in depth — grounded from types.py docstrings only).

## Policies (`omnigent/policies/`, runtime engine referenced but not read: `omnigent.runtime.policies.engine.PolicyEngine`)

- **`FunctionPolicy`** — `omnigent/policies/function.py` (implements `Policy`, resolved via `resolve_function_policy`).
- `PromptPolicy` referenced in base.py docstring as sibling of FunctionPolicy but `prompt.py` was not opened.
- **`EvaluationContext`** (frozen dataclass) — `omnigent/policies/types.py:68-203`. phase, content, tool_name, trajectory, actor, session_state, usage, model, harness, labels, llm_client.
- **`PolicyResult`** (frozen dataclass) — types.py:207-276. action (ALLOW/ASK/DENY), reason, set_labels, deciding_policies, data (transform payload), state_updates.
- **`ElicitationRequest`** — types.py:280-331. MCP-elicitation-shaped ASK payload (message, requestedSchema, policy_names).
- **`PolicyLLMClient`** — types.py:335-475. Pre-bound LLM client for policy callables, with serial fallback-model retry on `.create()`.
- **Runner-side mirror: `RunnerToolPolicyGate`** — `omnigent/runner/policy.py:109-306`. Re-implements TOOL_CALL/TOOL_RESULT-only enforcement locally on the runner (constructed per spec_hash via `.from_spec()`) so MCP tool dispatch doesn't round-trip to the server for the fast ALLOW/DENY path; ASK escalates back to the server via `pending_approvals`. `PolicyVerdict` (frozen dataclass, policy.py:65-101) is its return type: `action: "allow"|"deny"|"ask"`.

- **`ExecutorEvent`** family (all dataclasses, executor.py:96-260): `TextChunk`, `ReasoningChunk`, `ToolCallRequest`, `TurnComplete`, `ToolCallComplete`, `CompactionComplete`, `TurnCancelled`, `ExecutorError`. `ToolCallStatus` enum (SUCCESS/ERROR/BLOCKED/CANCELLED).

## MCP tooling (`omnigent/tools/mcp.py`, `omnigent/runner/mcp_manager.py`)
- **`McpServerConnection`** (dataclass) — `tools/mcp.py:392-1085`. Owns one MCP server's lifecycle on a dedicated asyncio task (`_run_lifecycle`, tools/mcp.py:671) for anyio cancel-scope-identity correctness. `connect()`→discovers tools (cached via module-level `_discovery_cache` TTLCache, 5min TTL); `call_tool()`→`_call_tool_with_reconnect` with exponential backoff; `_CircuitBreaker` (tools/mcp.py:211-323, trips after 5 consecutive failures, 30s cooldown, half-open probe) wraps every call. Supports MRTR elicitation (`McpElicitationRequired`, `call_tool_with_elicitation`). Transports: stdio (unsandboxed subprocess) or HTTP (Streamable-HTTP-first, SSE fallback).
- **`RunnerMcpManager`** — `omnigent/runner/mcp_manager.py:203-787`. Runner-side pool that shares `McpServerConnection`s across sessions keyed by spec_hash (`compute_spec_hash`, mcp_manager.py:87), with `_SharedServerEntry`/`_SpecEntry` ref-counting and eviction. `prewarm(spec)`, `schemas_for(spec)`, `call_tool(...)`.

## CLI / Host
- CLI entry: `omnigent/cli.py`, Click-based (`@click.group(cls=_OmnigentCLI)` at cli.py:1285). `omni host` group at cli.py:6995-7102 — the `host()` command IS the daemon (foreground); no server URL ⇒ spawns/reuses a local server via `ensure_local_omnigent_server()`, else does Databricks sign-in preflight (`_ensure_databricks_server_auth`) then calls `run_host_process(server_url=server)` (→ `omnigent/host/connect.py`).
- **`HostIdentity`** (dataclass) — `omnigent/host/identity.py:40-51`. `host_id` (`host_{uuid4hex}`), `name`. `load_or_create_host_identity()` (identity.py:54) reads/writes `~/.omnigent/config.yaml`, with an env-var override path for server-managed sandbox hosts (`OMNIGENT_HOST_TOKEN`/`_ID`/`_NAME`).
- **`HostProcess`** — `omnigent/host/connect.py:626` class (init ~637). Owns the WS tunnel client loop, `self._runners: dict[str, _RunnerHandle]`, reconnect state.
- Host↔server frames — `omnigent/host/frames.py`: `HostFrameKind` enum (frames.py:37-57: HELLO, LAUNCH_RUNNER(+RESULT), STOP_RUNNER(+RESULT), RUNNER_EXITED, STAT/LIST_DIR/CREATE_WORKTREE/REMOVE_WORKTREE/LIST_WORKTREES/CREATE_DIR (+RESULT)). Dataclasses: `HostHelloFrame` (64-89), `HostLaunchRunnerFrame` (93-119), `HostLaunchRunnerResultFrame` (123-146), `HostRunnerExitedFrame` (180-200, one-way, no result frame).
- **`HostRegistry`** (server-side) — `omnigent/server/host_registry.py:223`. Thread-safe (`threading.RLock`) in-memory map of live host WS connections per replica; `register()`/`deregister()`/`get()`/`send_text()` (enqueues onto an `asyncio.Queue`, NOT thread-safe across event loops — must be called on the host WS's owning loop).
- **`RunnerToolDispatch`** etc. in `omnigent/runner/app.py` / `omnigent/runner/tool_dispatch.py` — not opened; app.py (19k+ lines) is dominated by per-harness `_auto_create_<harness>_terminal` functions, strongly suggesting the runner is a single large FastAPI app module rather than a clean class hierarchy (**UNCERTAINTY**: no obvious `Runner` class — appears to be a module-level FastAPI app + free functions).
- **`pending_approvals`** module (not a class) — `omnigent/runner/pending_approvals.py`. Process-global `dict[str, asyncio.Future[bool]]` registry (`register`/`resolve`/`cleanup`/`wait_for_user_approval` at pending_approvals.py:133-198, default 86400s wait).

# RELATIONSHIPS
- `AgentSpec` --owns--> `ExecutorSpec`, `LLMConfig`, `ToolsConfig`, `GuardrailsSpec`, `list[MCPServerConfig]`, `list[SkillSpec]`, `list[AgentSpec]` (sub_agents, recursive).
- `GuardrailsSpec` --owns--> `list[PolicySpec]` (base) / `FunctionPolicySpec` (subclass) --owns--> `FunctionRef`.
- `FunctionPolicy` --implements--> `Policy` (ABC).
- `RunnerToolPolicyGate` --creates/owns--> `list[_GatedPolicy]` --wraps--> `FunctionPolicy` (via `resolve_function_policy`); built `.from_spec(AgentSpec)`.
- `RunnerToolPolicyGate.evaluate_tool_call/_result` --calls--> `Policy.evaluate(EvaluationContext, ...)` --returns--> `PolicyResult` --composed into--> `PolicyVerdict`.
- `Executor` (base) --implemented by--> `*Executor` subclasses in `omnigent/inner/` (one per harness). `Executor.run_turn` --yields--> `ExecutorEvent` subclasses.
- `LoadedAgent` --owns--> `AgentSpec` + `workdir: Path`; produced by `AgentCache.load()` (not read).
- `Conversation` --references--> `agent_id`, `runner_id`, `host_id` (foreign-key-style string ids, not object refs) — DB-flavored entity, not an OOP composition.
- `ConversationItem` --owns--> `ItemData` (discriminated union of 11 pydantic models) via `data` field; `NewConversationItem`/`ConversationItem` both validate `type` matches `data`'s class (`_validate_type_matches_data`).
- `McpServerConnection` --owned/shared by--> `RunnerMcpManager` (ref-counted via `_SharedServerEntry`); `RunnerMcpManager.call_tool` --calls--> `McpServerConnection.call_tool` --calls--> `_call_tool_with_reconnect` --uses--> `_CircuitBreaker`.
- `HostProcess` --creates/owns--> subprocess `_RunnerHandle` (Popen) per launched runner, keyed by `runner_id` (derived from `token_bound_runner_id(binding_token)`).
- `HostRegistry` (server) --tracks--> `HostConnection` per connected `HostProcess` (client); server --sends--> `HostLaunchRunnerFrame` over the WS the `HostRegistry` tracks --host replies--> `HostLaunchRunnerResultFrame`.
- `PolicyLLMClient` --wraps--> `omnigent.llms.client.Client` (not opened) with server-level model/connection pre-bound; used inside `EvaluationContext.llm_client` for `PromptPolicy`-style callables.

# WORKFLOW TRACES

## (a) Host initialization / auth / WS connect / HostHello / registered
1. `omnigent host [--server URL]` invoked → `omnigent/cli.py:7009 host()`. If no `--server`, resolves from config; if still empty, spawns/reuses a local server via `ensure_local_omnigent_server()` (cli.py:7065).
2. If remote + Databricks-fronted, preflight sign-in: `_ensure_databricks_server_auth(server, non_interactive=...)` (cli.py:7086) — runs the same browser login flow as `omnigent login` unless `--non-interactive`.
3. `run_host_process(server_url=server)` (cli.py:7087) → `omnigent/host/connect.py` constructs a `HostProcess` and calls `.run()` (connect.py:1612).
4. `HostProcess.run()` (connect.py:1612-1708): starts an orphan-reaper background task, then loops `await self._connect_and_serve()` inside a try/except that classifies disconnects and backs off exponentially (`backoff = min(backoff*2*(1+jitter), _RECONNECT_CAP_S)`, connect.py:1694) — except explicit server-recycle codes (1012/1001) or ingress bounces (502/no-close-frame on non-loopback) which get a fast fixed-`_RECONNECT_BASE_S` retry (connect.py:1674-1681). `HostConnectError` (permanent — bad auth) is NOT retried, propagates out.
5. `_connect_and_serve()` (connect.py:1726-1772): builds WS upgrade headers via `_build_connect_headers()` (connect.py:1774-1825) — either the managed-sandbox `X-Omnigent-Host-Token` header, or a freshly-minted Databricks bearer token via `_make_auth_token_factory` (from `omnigent/runner/_entry.py`). Opens `websockets.asyncio.client.connect(url, additional_headers=headers, ping_interval=TUNNEL_KEEPALIVE_PING_INTERVAL_S, ...)`. Fatal upgrade errors (`InvalidURI`/`InvalidStatus`) are classified via `_fatal_upgrade_error` — permanent failures raise `HostConnectError` and skip retry.
6. `_serve_frames(ws)` (connect.py:1827-1884): sends `HostHelloFrame` (version, frame_protocol_version=1, name, `runners=self._alive_runner_ids()`, `configured_harnesses=configured_harness_map()` off-thread, telemetry_opt_out) — connect.py:1847-1859. Prints the "✓ Connected" banner (connect.py:1871). Then loops `ws.recv()` with a 60s timeout, dispatching each frame.
7. Server side: receives `host.hello` over the host tunnel router (`create_host_tunnel_router`, `server/app.py` ~2358) → registers via `HostRegistry.register(host_id, ws, hello, owner)` (host_registry.py:238-274) — replaces+poisons any stale prior connection for the same host_id.
8. Login-flow branch: if the server redirects the WS upgrade to a login page (unauthenticated), `_login_redirect_streak` increments; `run()` classifies this as a permanent `HostConnectError` after enough consecutive redirects — surfaces "run `omnigent login`" rather than retrying forever (connect.py ~1638-1651; exact streak threshold not read in full).

## (c) Message/steering flow during a session — grounded in `docs/QUEUE_STEER_DESIGN.md`
1. User types a follow-up while the agent is busy → held **client-side** in a pre-POST draft queue (localStorage-persisted, keyed by session) — NOT sent to the server yet (QUEUE_STEER_DESIGN.md:23-36). This is a stated redesign away from the old "POST immediately" behavior.
2. Two ways a queued message reaches the server: (i) **auto-flush on idle** — when `sessionStatus` goes idle, the FIFO head is sent as the next normal turn; (ii) **Steer** — user explicitly jumps the queue, POSTs immediately regardless of busy state (QUEUE_STEER_DESIGN.md:40-53, 68-76).
3. Delivery mechanism is harness-specific (table at QUEUE_STEER_DESIGN.md:78-87): SDK harnesses (claude-sdk/codex-sdk/pi-sdk) use the runner's **live injection** gate (`_live_response_id`) via `Executor.enqueue_session_message()` (executor.py:573-575, default False/no-op, overridden per-executor) for deterministic mid-turn delivery. Native harnesses without a live-steer RPC (cursor-native, pi-native, etc.) do `send-keys` paste into the live tmux pane or queue to a resident extension (`supports_enqueue=True`); opencode-native has no live-steer endpoint at all — a steered message is admitted as a brand-new prompt, promoted only at the next turn boundary.
4. **Steer is explicitly NOT interrupt** — the running turn is never cancelled; the message folds in at the agent's next natural breakpoint (QUEUE_STEER_DESIGN.md:106-112). A separate Interrupt button calls `turn.cancel()`.
5. All native `run_turn` implementations return immediately after delivering the input (decoupled from the response) — "no runner change is required for native steer" (QUEUE_STEER_DESIGN.md:98-104).
6. **UNCERTAINTY**: the actual SSE/streaming fan-out from runner→server→client (sync vs async at each hop) was not traced here — requires `omnigent/runner/routing.py`, `omnigent/runtime/session_stream.py`, `omnigent/runtime/user_session_stream.py`, and the server's `_runner_transport.py`/`_runner_ws_tunnel.py`. See the server-subsystem report for the delivery-mechanism table.

## (d) Policy/approval flow — harness wants a risky tool → pending approval → user approves → tool proceeds
1. Harness (via its Executor) emits `ToolCallRequest` (executor.py:134-146).
2. Runner-local fast path: `RunnerToolPolicyGate.evaluate_tool_call(tool_name, arguments)` (runner/policy.py:159-182) builds an `EvaluationContext(phase=Phase.TOOL_CALL, ...)` and walks `_GatedPolicy` entries via `_evaluate_policies` (policy.py:228-306): each `FunctionPolicy.evaluate()` is awaited; **DENY short-circuits immediately**; **ASK is recorded but evaluation continues** (a later policy can still escalate to DENY); ALLOW/no-match continues. A raised exception in a policy callable is treated as fail-closed DENY (policy.py:263-279).
3. On `PolicyVerdict(action="ask", ...)`, the caller (runner's tool_dispatch) escalates by POSTing `evaluate_policy=True` to the Omnigent server — per policy.py:20-24 docstring, the runner's local gate doesn't own an elicitation channel, only the server does (it needs `ConversationStore` + can render the approval UI).
4. Server independently re-evaluates (its own `PolicyEngine`, in `omnigent.runtime.policies.engine`, not opened) and parks an `ElicitationRequest` (policies/types.py:280-331) — this is what the sidebar "pending approval" badge reflects.
5. Runner awaits the verdict: `pending_approvals.wait_for_user_approval(elicitation_id, conversation_id, publish_event, timeout_seconds)` (pending_approvals.py:133-198) — registers an `asyncio.Future[bool]` (`register()`, pending_approvals.py:79-94), marks the session "awaiting approval" via `_session_pending` (so a mid-flight `sys_session_send` injection from a parent agent doesn't perturb the parked turn — pending_approvals.py:51-60), and `asyncio.wait_for(fut, timeout=effective_timeout)` (default 86400s, one full day — an ASK is meant to survive the user stepping away).
6. User approves from any connected device → server POSTs to `/v1/sessions/{id}/events` (referenced in pending_approvals.py:5) → runner's session-event handler calls `pending_approvals.resolve(elicitation_id, approved=True)` (pending_approvals.py:110-130), which sets the Future's result.
7. `wait_for_user_approval` returns `True`; on the way out (every exit path — verdict, decline, timeout, or cancellation) it publishes `response.elicitation_resolved` so the server's pending-elicitations index (and the UI badge) stays in lockstep (pending_approvals.py:186-197).
8. Tool proceeds — the caller uses the boolean verdict to either dispatch the tool call for real or synthesize a denial via `format_deny_text(policy_name, reason)` (policy.py:314-336), which the LLM sees as the tool's output (`"[Denied by policy: <name>] {...}"`).
9. **Fail-closed phases**: `FAIL_CLOSED_PHASES = ("PHASE_TOOL_CALL", "PHASE_REQUEST")` (policies/types.py:64) — an unevaluable policy on these phases denies rather than allows; `PHASE_TOOL_RESULT` fails open since the tool already ran by then (policies/types.py:56-59).

## (e) Failure/retry — host-tunnel reconnect (see workflow (a) step 4) and runner-exit reporting:
- `HostRunnerExitedFrame` (frames.py:180-200) is a **one-way** report (no result frame) — the host daemon watches every runner subprocess it spawned (`_watch_runner`, connect.py:1192) and on unexpected exit composes exit code + log tail, sends it. Server stashes via `RunnerExitReports` (host_registry.py:39-60, TTL 600s / max 1024 entries) so a client polling a never-connecting runner learns *why* instead of timing out.
- If the host tunnel itself is down when a runner dies, the exit report is parked in `self._unreported_exits` (connect.py ~1229-1240) and flushed on the next successful reconnect (`_serve_frames`, connect.py:1864-1866) — **state survives the host-tunnel drop; nothing is re-derived**, it's just queued client-side.
- On server restart: `_on_runner_connect` callback (server/app.py ~2230+) re-derives session↔runner bindings by querying `conversation_store.list_conversations_by_runner_id(runner_id)` (a DB query, not in-memory state) for every reconnecting runner, re-POSTs `/v1/sessions` session-init for each bound conversation that has an `agent_id`, re-establishes the SSE relay (`_ensure_runner_relay`), and clears any `runner_disconnected` status label via `_publish_runner_recovered_status(require_disconnect_code=True)` — so **the DB conversation row (runner_id, agent_id, labels) is the source of truth that survives a server restart; the in-memory `HostRegistry`/relay state is fully re-derived from it.**
- Workflow (b) (session launch end-to-end) was not traced step-by-step here beyond confirming the pieces: `HostRegistry.send_text` enqueues the `HostLaunchRunnerFrame`; `HostProcess._handle_launch` (connect.py:1029-1155) validates harness availability (`harness_is_configured`), spawns `python -m omnigent.runner._entry` via `subprocess.Popen` with `binding_token`/`workspace` in env, returns `HostLaunchRunnerResultFrame`. The server-side orchestration that decides *when* to send `host.launch_runner` (likely `omnigent/server/routes/sessions.py`) and the runner's own startup sequence in `runner/_entry.py` (`create_app`, `_run_tunnel_from_env`) were not stepped through function-by-function — the host+runner report is authoritative for (b).
