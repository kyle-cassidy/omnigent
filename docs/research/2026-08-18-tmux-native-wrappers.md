## 1. tmux invocation inventory

**Base command / socket.** `omnigent/inner/terminal.py:993-1006` (`_tmux_base_cmd`): `tmux -S <socket_path> -f /dev/null`. The `-f /dev/null` deliberately ignores the user's own `~/.tmux.conf`. Socket path is **not** hash-derived: `terminal.py:1891-1892` does `tempfile.mkdtemp(prefix="omnigent-terminal-")/tmux.sock` — every `TerminalInstance` gets its own **private tmux server**, not a shared server with many sessions.

**Session naming.** `tmux_target` is hardcoded to the literal string `"main"` (`terminal.py:951-953`). Since each terminal owns a private server, there's never a need to disambiguate — the socket path *is* the identity.

**new-session.** `terminal.py:1123-1147`: `new-session -d -s main -x 80 -y 24 -c <cwd> <inner_cmd>`, preceded by option commands (`terminal.py:226-377`): history-limit, extended-keys/mouse/focus-events, `escape-time 0`, a lockdown block (`prefix None`, unbinding the whole prefix table + mouse-3 context menu so an attached human can't spawn stray panes), and a custom status line. Optionally followed by `remain-on-exit on` (`terminal.py:257-289`) — the load-bearing option for "session survives the CLI exiting."

**send-keys.** Literal text: `send-keys -l -t main <chunk>`, chunked at 1024 chars (`terminal.py:1165-1213`) because tmux's client→server IPC caps a single command near 16KB. Special keys (Enter, Escape, Ctrl-A/K/U) sent as separate `send-keys -t main <key>` calls throughout every `*_native_bridge.py` file (e.g. `claude_native_bridge.py:2543-2597`, `hermes_native_bridge.py:707-740`, `goose_native_bridge.py:294-328`, `kiro_native_bridge.py:592-755`).

**Buffer-paste (bypasses the 16KB cap).** Not centralized in `terminal.py` — duplicated per harness: `claude_native_bridge.py:2559-2578` writes payload to a temp file, `load-buffer -b omnigent-paste <path>`, then `paste-buffer -p -d -b omnigent-paste -t <target>` (`-p` = bracketed-paste so embedded newlines don't submit early). Same pattern in `hermes_native_bridge.py:~716-724`, `goose_native_bridge.py:270-306`, `antigravity_native_bridge.py:~1048`.

**capture-pane.** Reading pane content back: `terminal.py:1215-1240` (`read()`), idle-watcher polling (`terminal.py:1409-1416`, 1s interval), and `control_bridge.py:153-228` (seeds a freshly-attached browser client, since control-mode clients only see output *after* attach).

**pipe-pane.** Confirmed **absent** — `grep -rn "pipe-pane" omnigent/` returns zero hits anywhere in the package. No background pane logging/mirroring via pipe-pane; live viewing goes through the attach bridges instead.

**kill-session / kill-server / liveness.** `terminal.py` close() uses `kill-server` (kills the whole private server). Per-harness bridges use `kill-session` (`claude_native_bridge.py:2688`, `hermes_native_bridge.py:833`, `goose_native_bridge.py:354`, `kiro_native_bridge.py:653`, `qwen_native_bridge.py:789`, `cursor_native_bridge.py:862`) and `codex_native_process_registry.py:412` (orphan reaping). Notably, **core `terminal.py` never calls `has-session`** — it uses `list-panes -t main -F "#{pane_dead}"` instead (`terminal.py:1634-1656,1706-1766`), because `remain-on-exit` keeps the session alive after the CLI exits, so `has-session` alone can't distinguish "detached" from "the agent crashed." `has-session` **is** used, but only in the per-harness bridge readiness probes and the REPL: `hermes_native_bridge.py:575`, `goose_native_bridge.py:211`, `antigravity_native_bridge.py:1035`, `kimi_native_bridge.py:257`, `cursor_native_bridge.py:550`, `kiro_native_bridge.py:343`, `codex_native_process_registry.py:398`, `repl/_repl.py:7172`.

**Other commands.** `display-popup` for the cost-approval overlay (`native_cost_popup.py`); `list-clients -t main` as the "is a human attached" liveness signal feeding the idle-pane reaper (`native_cost_popup.py:45,106`); `attach [-r] -t main` forked onto a real PTY (`terminals/ws_bridge.py:547`) or via `-C` control mode (`terminals/control_bridge.py:354-357`); `send-keys -H <hex>` for control-mode input (raw ESC bytes would corrupt tmux's line-based control parser); `set-option -p -t <pane>` in the REPL's optional (disabled-by-default) outer-pane integration (`repl/_tmux_pane.py`, unrelated to the managed terminals).

## 2. Per-wrapper architecture (claude-native as the representative case)

`claude_native.py`'s docstring: *"creates or binds an Omnigent session, launches `claude` through the existing runner terminal resource API, then attaches the local TTY to the existing terminal WebSocket protocol."*

- **"Runner terminal resource API"** = REST CRUD over `/v1/sessions/{id}/resources/terminals[/{id}]`, backed by `SessionResourceRegistry`/`TerminalRegistry` (`runner/resource_registry.py`, `runner/app.py:15782`). POST launches (or, with `ensure_native_terminal: true`, routes to `_auto_create_claude_terminal`, `app.py:5347`); GET looks it up; DELETE tears it down. The terminal id is deterministic (`terminal_resource_id("claude","main")`).
- **"Terminal WebSocket protocol"** = `wss://.../resources/terminals/{id}/attach`. Server→client: binary frames of raw PTY bytes. Client→server: JSON text frames (`{"type":"resize",...}`) or binary keystroke frames (`server/routes/terminal_attach.py` docstring). In-process it's bridged by `terminals/ws_bridge.py` (real forked `tmux attach` on a PTY) or `terminals/control_bridge.py` (tmux control-mode); cross-machine (out-of-process runner) it's multiplexed over one outbound tunnel connection via `server/_runner_ws_tunnel.py` + `runner/transports/ws_tunnel/frames.py` (`WSOpenFrame`/`WSFrame`/`WSCloseFrame`), because the runner only has outbound connectivity to the server.

**`claude_native_bridge.py`** is a *separate* concern from the above: rendezvous between two live processes — Claude Code sitting in the tmux pane, and the short-lived "harness turn" process spawned when the web UI submits a message. Its own docstring is explicit: this exists because *"Claude's experimental Channels MCP capability was the original input path but is blocked at the org policy layer, so this bridge does not use it"* — tmux send-keys/paste-buffer is the fallback, not the first choice. The runner writes a small `tmux.json` (socket + target) into a bridge dir once the terminal launches (`write_tmux_target`, called from `runner/app.py` after `_auto_create_claude_terminal`); the bridge polls for that file before doing anything.

**forwarder / hook / state / status** (also present per-harness for codex, cursor, etc.):
- `claude_native_hook.py` — the *actual* Claude Code hook script, injected via `--settings <json>` on the CLI invocation (not by mutating `~/.claude/settings.json`). Claude spawns it as a subprocess per hook event (PreToolUse, Stop, UserPromptSubmit, TaskCreated, PreCompact, etc.); it appends events to a bridge-dir file and, for hooks needing a synchronous decision (permission requests, ask-user-question, policy evaluation), POSTs to the omnigent server and prints a verdict back to stdout for Claude to consume.
- `claude_native_forwarder.py` — background `asyncio` task that tails those bridge-dir files (hook events, Claude's own transcript JSONL, streamed message-delta chunks) and POSTs structured events (`external_conversation_item`, `external_session_status`, etc.) to `/v1/sessions/{id}/events`. Pure read-and-relay; it does not register hooks itself.
- `claude_native_state.py` — persists the launch cwd per conversation at `~/.omnigent/claude-native/<sha256(conv_id)[:32]>/launch.json`, needed because Claude's `--resume <sid>` requires a matching cwd — a client-side fact, deliberately not sent to the server.
- `claude_native_status.py` — wraps Claude's `statusLine.command` to capture live context-window usage into the bridge dir, then execs the user's real statusline command so terminal rendering is unaffected.

Generic infra shared across all ten native wrappers: `native_cost_popup.py` (tmux popup for budget approval), `native_policy_hook.py` (shared PreToolUse/policy-evaluation translation used by both Claude and Codex hooks), `native_server_harness.py`/`native_server_transport.py` (the *non-tmux* variant used by codex-native's WS JSON-RPC and opencode-native's HTTP/SSE — not used by claude-native itself), `native_terminal.py` (shared `terminal_attach_url` builder).

## 3. Cross-process sync mechanism, step by step

1. Runner launches the vendor CLI inside a private tmux pane and publishes a `tmux.json` rendezvous file once ready.
2. **Structured conversation mirroring does not go through tmux at all.** For Claude, the hook script writes events to bridge-dir files that the forwarder tails. For Codex, it's not file-tailing — `codex_native_app_server.py` runs a persistent JSON-RPC-over-WebSocket client against a **second, headless "app-server" process omnigent itself spawns**, and `codex_native_forwarder.py` does `async for event in client.iter_events()`, a live push subscription (confirmed zero `watchdog`/`inotify`/`FSEvents` usage anywhere in the package).
3. Either way, the forwarder POSTs to `/v1/sessions/{id}/events` on the omnigent server. `server/routes/sessions.py:5110-5186` (`_persist_external_conversation_item`) durably appends to `conversation_store` (the DB) **and** publishes to an in-process pub/sub keyed by conversation id (`runtime/session_stream.py` — explicitly no replay buffer, "events emitted before a subscriber connects are lost").
4. Any connected client holds `GET /v1/sessions/{id}/stream` (SSE) open and gets live pushes; a reconnecting/new client instead fetches the `GET /v1/sessions/{id}` snapshot and dedupes by item id.
5. **Separately**, if a human wants to literally watch the raw terminal (not just structured chat), that's the `/attach` WebSocket route from part 2, streaming actual tmux pane bytes — a parallel, independent path from the structured mirror above.
6. Process bookkeeping: `codex_native_process_registry.py` keeps a single global `~/.omnigent/codex-native/process-registry.json` (pid, pgid, tmux_session_name, a unique cmdline tag) guarded by per-launcher `flock` files under `process-owners/`. On next launch, a dead launcher is detected by its released flock, its orphaned tmux session is verified via cmdline-tag match (PID-reuse safety) and reaped with `kill-session` + `SIGTERM` on the process group — so a crashed CLI doesn't leave a zombie tmux server running Codex forever.
7. Per-session state directories follow one convention package-wide: `~/.omnigent/<harness>-native/<sha256(id)[:32]>/` (confirmed for codex, claude, opencode, and by pattern for others) holding client-local facts (launch cwd, bridge sockets, dead-letter queues for undelivered events) that must survive CLI restarts but shouldn't leak to the server.

## 4. Detach/reattach — "device follows you"

- `remain-on-exit on` is what makes the tmux session outlive a detaching client at all.
- The CLI's own attach loop distinguishes `EXITED` vs `DETACHED` (`claude_native.py:1970-1998`). On `DETACHED` it explicitly does **not** close the terminal resource and does **not** tear down the runner — comment: *"the daemon owns the runner... the web UI keeps rendering it"* — so the process and its tmux pane are left running, owned by the runner/daemon rather than the CLI.
- Same-machine fast path attaches the local TTY directly to the tmux socket; cross-machine falls back to the WS PTY bridge over the tunnel.
- A phone or browser reattaching goes through the *identical* `/attach` route and, since tmux natively supports multiple simultaneous clients per session, lands on the **same live pane** — genuine session mirroring (owner = read/write, others = read-only, enforced by `LEVEL_OWNER` vs `LEVEL_READ` in `terminal_attach.py`), not a state-replay trick.
- Resume is two-tiered: `_resume_picker.py` is pure metadata (lists sessions, no tmux contact); the downstream native module then tries a warm reattach to a live tmux session first, falling back to a cold resume (fresh terminal + the vendor CLI's own `--resume` against its transcript) only if none is live.

## 5. Sandboxing

tmux itself is **always unsandboxed**, host-side (`terminal.py:1036`). Only the inner CLI process launched *inside* the pane gets wrapped — the sandbox launcher script becomes the pane's shell command (`terminal.py:1063-1090` → `inner/sandbox.py`, dispatching to `bwrap_sandbox.py` on Linux or `seatbelt_sandbox.py` on macOS). A specific, named mitigation exists purely because tmux's control socket is a live coordination channel: `with_denied_unix_sockets` (`terminal.py:1941-1949`) blocks the sandboxed pane process from reaching back into the unsandboxed tmux server (comment: it could otherwise `tmux -S <sock> run-shell` against its own controller) — implemented as a bind-mask over the socket path on Linux and an explicit deny rule on macOS, plus stripping `OMNIGENT_TMUX_SOCK` from the inherited environment as defense in depth.

## 6. What breaks without tmux

Every `omnigent <harness>-native` command is entirely unusable without tmux: a local `shutil.which("tmux")` preflight raises `click.ClickException` before anything launches (present in all ten `*_native.py` modules), and even bypassing that, the runner-side `create_terminal_instance` hard-fails with `RuntimeError("tmux is not installed or not on PATH")` — enforced independently on both the wrapper machine and the runner machine. Native-wrapper mode is also rejected outright on Windows for the same PTY reason. Critically, **any** agent-granted `sys_terminal_launch` tool call — regardless of which harness is driving the conversation — funnels through this same choke point, so tmux gates general terminal capability, not just the native wrappers.

What is **unaffected** by tmux's absence: `SDK_IN_PROCESS` harnesses (claude-sdk, openai-agents, cursor, antigravity, copilot, open-responses), `CLI_SUBPROCESS` (the plain, non-`-native` codex/pi/kimi/hermes), and `ACP_SUBPROCESS` (acp/goose/qwen) — these have `Resume.COLD_ONLY` or app-server-level resume, i.e. transcript replay rather than live-process reattachment, and never touch tmux. One instructive hybrid: `opencode-native` is classified `NATIVE_SERVER` (its actual model-driving protocol is HTTP/SSE, not send-keys injection), yet its CLI wrapper still hard-requires tmux — purely for mirroring its TUI into a viewable/attachable pane. That's a clean natural experiment showing tmux's role split in two: driving the model doesn't need it, but the live-viewing/attach/continuity experience does.

## Verdict: coordination layer, not "just a multiplexer" — but scoped, not universal

Within the native-wrapper subsystem, tmux is doing real architectural work, not incidental terminal display:

1. **It's the input-delivery mechanism where no API exists.** Claude Code's own MCP input channel is blocked at the org policy layer (per the bridge's own docstring), so `send-keys`/`paste-buffer` is the *only* way web-UI messages reach the running CLI. This isn't convenience — it's the sole path.
2. **It's the continuity substrate for "device follows you."** `remain-on-exit` + native multi-client attach is what lets a laptop detach and a phone reattach to the *same live process* with zero bespoke state-transfer protocol — that's a session, not a snapshot, being handed across devices.
3. **It's a security boundary worth defending.** The sandbox model treats the tmux control socket as sensitive enough to explicitly deny-list — evidence that tmux is a live coordination channel between processes at different trust levels, not inert scrollback.
4. **Isolation is deliberate:** one private tmux server per terminal (random socket, not a shared multiplexer instance) — this is closer to "tmux used as a lightweight per-session PTY-hosting daemon" than to a human multiplexing panes.

But it is explicitly **not** how structured conversation state syncs across the platform — that's a completely separate hook/forwarder → HTTP POST → DB + SSE pub/sub pipeline that never touches tmux, and most of omnigent's harness surface (SDK/CLI-subprocess/ACP modes) runs with no tmux involvement at all. So the accurate framing: **tmux is a load-bearing coordination layer specifically for the `NATIVE_TUI` wrapper family** (session hosting, input injection, live multi-device viewing, detach/reattach), sitting alongside — not underneath — omnigent's general-purpose HTTP/WebSocket/SSE coordination plane that the rest of the platform runs on.

## Uncertainties (from the four parallel research passes)

- The 8 per-harness `_run_tmux`/buffer-paste implementations were confirmed structurally identical in the one fully-read file (`claude_native_bridge.py`) and via docstrings/grep on others (hermes, goose, antigravity) — not diffed byte-for-byte across all ten.
- `runner/app.py`'s `_auto_create_claude_terminal` (multi-hundred-line cold-resume/ucode-auth flow) and the `NativePaneReaper` wiring in the same file were read only enough to confirm call sites, not exhaustively.
- Whether `session_stream.py`'s in-process SSE pub/sub has a cross-replica fan-out layer (Redis, Postgres LISTEN/NOTIFY) for multi-process server deployments was not found or confirmed — plausible gap in a horizontally-scaled deployment, not verified either way.
- The "daemon" that is said to "own the runner" on CLI detach is referenced by comments in `claude_native.py` but its concrete source module wasn't located in this pass.
- Whether plain `codex` (non-native, `CLI_SUBPROCESS`)'s declared `Resume.WARM_REATTACH` maps to a literal live-process reattach or just its app-server's own resume concept (no PTY) wasn't resolved — a taxonomy vs. mechanism gap worth a follow-up read if it matters.
- Not verified whether native-wrapper chat (SSE/ApprovalCard) keeps working if only the terminal-attach feature is broken by missing tmux — plausible given how the two paths are architecturally separate (section 3 vs section 4), but not directly traced end-to-end.
